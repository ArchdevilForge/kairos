  "objective": "# Goal: 市场整体异动监控（Market Pulse）\n\n> 状态：Draft / 可直接执行  \n> 目标仓库：`ArchdevilForge/kairos`  \n> 建议路径：`docs/GOAL_MARKET_PULSE.md`  \n> 核心原则：只有市场从安静状态切换到整体活跃时才叫醒用户；单币异动只用于解释谁在领涨或领跌。  \n> 实施优先级：P0 价格广度 → P1 告警门控 → P2 衍生品确认 → P3 板块扩散。\n\n---\n\n## 0. 一句话目标\n\n将 Kairos 从“监控某个币突然涨跌”升级为：\n\n> 监控整个加密永续市场何时从安静切换为同步上涨、同步下跌、趋势扩散或系统性高波动，只在真正值得打开盘面时发送 Telegram 告警。\n\n最终 Kairos 应回答三个问题：\n\n1. **现在是否值得看盘？**\n2. **市场整体正在向上、向下，还是只有局部币种异动？**\n3. **哪些币最能代表这次市场趋势？**\n\n---\n\n## 1. 背景与当前问题\n\nKairos 当前已经具备：\n\n- 订阅成交量靠前的永续合约；\n- WebSocket 实时 ticker；\n- 单币价格速度检测；\n- 单币成交量、OI、资金费率等检测器扩展位；\n- 统一的事件 aggregator；\n- Telegram 告警、去重和冷却；\n- 单币多维度 resonance scorer。\n\n但当前告警核心仍然是：\n\n```text\n某个 symbol 在 60 秒或 120 秒内达到价格变化阈值\n```\n\n这会产生以下问题：\n\n1. 单币拉盘、插针、消息币异动会叫醒用户；\n2. 大量独立告警不代表市场存在可交易趋势；\n3. 用户打开盘面后，经常发现 BTC、ETH 和绝大多数币都没有同步；\n4. 单币事件无法直接判断行情是否具有扩散性和持续性；\n5. 告警关注的是“发生了什么”，而不是“现在值不值得看盘”。\n\n因此需要新增一个横跨所有监控币种的市场级检测层。\n\n---\n\n## 2. 第一性原理\n\n一个值得打开盘面的市场异动，通常至少具备以下特征：\n\n### 2.1 广度\n\n不是一个币在动，而是足够多的高流动性币种同时朝一个方向移动。\n\n### 2.2 幅度\n\n市场典型币种的涨跌幅超过正常短周期噪声，而不是仅仅多数币微涨 0.01%。\n\n### 2.3 同步性\n\n异动在相近时间内发生，而不是部分币一小时前涨、另一部分币刚开始涨。\n\n### 2.4 持续性\n\n条件持续多个采样周期，排除瞬时插针、WebSocket 抖动和盘口噪声。\n\n### 2.5 核心资产确认\n\nBTC、ETH 至少有一个与市场方向一致。若 BTC、ETH 完全不动，仅小币异动，更可能是局部板块行情。\n\n### 2.6 非集中驱动\n\n不能因为一个或两个高波动币暴涨，就把整个市场判定为上涨。\n\n因此市场级检测不能只使用平均涨幅，必须同时使用：\n\n```text\n市场中位收益率\n+ 上涨/下跌广度\n+ 标准化异常程度\n+ 持续确认\n+ BTC/ETH 核心确认\n+ 数据新鲜度\n```\n\n---\n\n## 3. Goal\n\n### 3.1 主目标\n\n新增 `MarketPulseDetector`，实时聚合当前监控 universe 的 ticker，识别并输出以下市场状态事件：\n\n```text\nmarket_impulse\nmarket_trend\nmarket_stress\nmarket_decay\n```\n\n并维护以下状态机：\n\n```text\nQUIET\nIMPULSE_UP\nIMPULSE_DOWN\nTRENDING_UP\nTRENDING_DOWN\nSTRESS_UP\nSTRESS_DOWN\nDECAY\n```\n\n### 3.2 用户体验目标\n\n默认情况下：\n\n- `QUIET` 时不发送普通单币价格异动；\n- 市场进入 `IMPULSE_*` 时发送一次叫醒告警；\n- 市场进入 `TRENDING_*` 时发送一次趋势确认；\n- 市场进入 `DECAY` 时可选发送趋势衰减；\n- 每条市场告警附带领涨或领跌币；\n- 避免同一轮行情重复刷屏。\n\n### 3.3 工程目标\n\n- 不新增独立微服务；\n- 不引入 Kafka、Redis 等额外基础设施；\n- 复用现有 ticker、aggregator、alert policy、Telegram 和 config；\n- 保持 Go 单体结构；\n- 核心算法必须确定性、可解释、可回放；\n- 不让 LLM 进入生产判断路径。\n\n---\n\n## 4. 非目标\n\n本 Goal 第一阶段明确不做：\n\n- 自动下单；\n- 预测未来涨跌；\n- 用 LLM 判断是否交易；\n- 复杂机器学习；\n- 基于新闻或社交媒体的行情解释；\n- 精确识别牛市、熊市大周期；\n- 完整板块分类；\n- 多交易所套利检测；\n- 订单簿微结构分析；\n- 将多个指标硬压缩成一个不可解释的“神奇分数”。\n\n第一版只回答：\n\n> 市场是否正在同步、显著、持续地移动。\n\n---\n\n## 5. 核心术语\n\n### 5.1 Universe\n\n本次市场统计实际参与计算的币种集合。\n\n默认：\n\n```text\nprimary exchange 上按 quote volume 排序的 Top 30 USDT 永续合约\n```\n\n### 5.2 Fresh Symbol\n\n在 `freshnessSeconds` 内收到过有效 ticker 的币种。\n\n### 5.3 Fresh Ratio\n\n```text\nfresh symbols / eligible symbols\n```\n\n新鲜度不足时禁止产生市场告警。\n\n### 5.4 Breadth\n\n满足方向条件的币种占有效币种比例。\n\n```text\nup_breadth = count(return > noise_threshold) / valid_count\ndown_breadth = count(return < -noise_threshold) / valid_count\n```\n\n### 5.5 Market Median Return\n\n所有有效币种滚动收益率的中位数。\n\n使用中位数而不是均值，避免极端币种污染。\n\n### 5.6 Median Z\n\n每个币滚动收益率除以自身近期 EWMA 波动率后，取横截面中位数。\n\n### 5.7 Leader\n\n相对于市场中位收益率表现最强或最弱的币种。\n\n---\n\n## 6. 事件定义\n\n## 6.1 `market_impulse`\n\n含义：\n\n> 市场从安静状态突然进入同步移动，值得立即打开盘面。\n\n事件方向：\n\n```text\nup\ndown\n```\n\n建议初始条件：\n\n```text\nfresh_ratio >= 0.80\nvalid_symbols >= 15\n同方向 breadth >= 0.65\nabs(median_return_60s) >= 0.18%\nabs(median_z_60s) >= 1.5\nBTC 或 ETH 至少一个同方向\n最近 4 个采样中至少 3 个满足\n```\n\n输出字段：\n\n```json\n{\n  \"direction\": \"up\",\n  \"state_from\": \"QUIET\",\n  \"state_to\": \"IMPULSE_UP\",\n  \"window_seconds\": 60,\n  \"median_return_pct\": 0.23,\n  \"median_z\": 1.82,\n  \"breadth\": 0.76,\n  \"advancers\": 22,\n  \"decliners\": 4,\n  \"neutral\": 3,\n  \"valid_symbols\": 29,\n  \"fresh_ratio\": 0.97,\n  \"btc_return_pct\": 0.31,\n  \"eth_return_pct\": 0.37,\n  \"leaders\": [\"SOL\", \"DOGE\", \"AVAX\"],\n  \"laggards\": [\"TRX\", \"XMR\", \"BCH\"]\n}\n```\n\n## 6.2 `market_trend`\n\n含义：\n\n> 市场启动后，方向继续扩散并持续，短周期趋势得到确认。\n\n建议条件：\n\n```text\n当前状态为 IMPULSE_UP 或 IMPULSE_DOWN\n同方向 breadth >= 0.60\nabs(median_return_300s) >= 0.45%\n方向持续 >= 180 秒\n最近 6 个采样中至少 5 个方向一致\n期间未进入反向 impulse\n```\n\n趋势状态：\n\n```text\nTRENDING_UP\nTRENDING_DOWN\n```\n\n## 6.3 `market_stress`\n\n含义：\n\n> 市场出现极端同步移动、恐慌下跌或逼空上涨。\n\n建议条件：\n\n```text\nfresh_ratio >= 0.80\n同方向 breadth >= 0.80\nabs(median_return_60s) >= 0.35%\nabs(median_z_60s) >= 2.5\n```\n\n后续 P2 可叠加：\n\n```text\n全市场爆仓异常\nOI 广度异常\n成交量广度异常\n```\n\n## 6.4 `market_decay`\n\n含义：\n\n> 已确认趋势开始失去广度或方向一致性，继续盯盘价值下降。\n\n建议条件：\n\n```text\n当前为 TRENDING_UP / TRENDING_DOWN\n同方向 breadth 连续 60 秒低于 0.50\n或 median_return_60s 接近 0\n或反方向 breadth 高于 0.45\n```\n\n默认可配置是否发送 Telegram。\n\n---\n\n## 7. 状态机\n\n```text\n                     ┌──────────────┐\n                     │    QUIET     │\n                     └──────┬───────┘\n                     impulse│\n             ┌──────────────┴──────────────┐\n             ▼                             ▼\n      ┌────────────┐                ┌────────────┐\n      │ IMPULSE_UP │                │IMPULSE_DOWN│\n      └──────┬─────┘                └─────┬──────┘\n             │ trend confirm              │ trend confirm\n             ▼                            ▼\n      ┌────────────┐                ┌─────────────┐\n      │TRENDING_UP │                │TRENDING_DOWN│\n      └──────┬─────┘                └──────┬──────┘\n             │ decay                       │ decay\n             └──────────────┬──────────────┘\n                            ▼\n                      ┌──────────┐\n                      │  DECAY   │\n                      └────┬─────┘\n                           │ reset\n                           ▼\n                        QUIET\n```\n\n### 7.1 反向切换\n\n若 `TRENDING_UP` 中直接满足强 `market_impulse down`：\n\n```text\nTRENDING_UP → DECAY → IMPULSE_DOWN\n```\n\n第一版不要直接一步翻转，以避免单次反向插针导致状态来回震荡。\n\n### 7.2 冷却\n\n建议：\n\n```text\n同状态重复事件 cooldown = 10 分钟\n状态变化事件不受普通 cooldown 限制\nstress 事件 cooldown = 5 分钟\n```\n\n### 7.3 重启恢复\n\nP0 可从 `QUIET` 冷启动。\n\nP1 可将当前状态与最近快照保存到 SQLite，重启后恢复，避免服务重启重复发送 impulse。\n\n---\n\n## 8. 数据结构设计\n\n新增文件：\n\n```text\ninternal/detector/market_pulse.go\n```\n\n建议类型：\n\n```go\ntype MarketState string\n\nconst (\n []pricePoint\n    LastSeen     float64\n    WarmupSince  float64\n    EWMA variance\n}\n```\n\n### 9.1 保存长度\n\n默认保留最近 15 分钟，足够覆盖：\n\n- 60 秒；\n- 180 秒；\n- 300 秒；\n- 波动率估计；\n- 调试回放。\n\n### 9.2 找历史价格\n\n不要假设 ticker 每秒固定到达。\n\n查找：\n\n```text\n距离 target timestamp 最近、但不晚于 target 的价格点\n```\n\n容差建议：\n\n```text\nmaxLookupGapSeconds = 15\n```\n\n若历史点缺失，则该 symbol 在该窗口无效。\n\n### 9.3 内存目标\n\nTop 30，每秒最多数次 ticker，保留 15 分钟时内存应保持很小。\n\n可通过以下方式控制：\n\n- 每 symbol 最多每秒记录一个价格；\n- pruning 删除窗口外点；\n- slice 或 ring buffer；\n- 第一版优先简单正确，不必提前做复杂优化。\n\n---\n\n## 10. 收益率与标准化\n\n### 10.1 收益率\n\n```text\nreturn_pct = (price_now / price_then - 1) * 100\n```\n\n### 10.2 噪声区间\n\n默认：\n\n```text\nnoiseReturnPct = 0.08\n```\n\n分类：\n\n```text\nreturn > +0.08%  => advancer\nreturn < -0.08%  => decliner\n其他             => neutral\n```\n\n### 10.3 EWMA 波动率\n\n建议使用 1 分钟收益的 EWMA 方差：\n\n```text\nvariance_t = alpha * r_t² + (1 - alpha) * variance_previous\nz = return_60s / max(sqrt(variance), volatility_floor)\n```\n\n初始：\n\n```text\nalpha = 0.10\nvolatility_floor_pct = 0.03\n```\n\n若 P0 时间有限，可先不使用 Z 作为硬门槛，只记录日志；但必须预留字段和测试。\n\n---\n\n## 11. Universe 管理\n\n当前 universe 会定时刷新，MarketPulse 必须正确处理成员变化。\n\n### 11.1 参与条件\n\n一个币参与计算必须满足：\n\n```text\n存在于当前 primary exchange universe\n不是 blacklist\nlast price > 0\n最近 freshnessSeconds 内收到 ticker\n已有至少 warmupSeconds 历史\n目标窗口存在可用历史价格\n```\n\n### 11.2 新币 warmup\n\n默认：\n\n```text\nwarmupSeconds = 300\n```\n\n新加入 universe 的币在 warmup 完成前不参与市场统计。\n\n### 11.3 被移除的币\n\n从 eligible universe 移除，但其历史缓存可延迟 15 分钟清理。\n\n### 11.4 Universe 变化保护\n\nuniverse 刷新后的 60 秒内：\n\n- 可以继续计算；\n- 禁止仅因成员变化触发新状态；\n- 若有效样本少于 `minValidSymbols`，保持原状态或进入数据不足状态，不发送方向告警。\n\n---\n\n## 12. 多交易所策略\n\nP0 只使用：\n\n```text\ncfg.Exchanges.Primary\n```\n\n原因：\n\n- 避免同一币在多个交易所重复计数；\n- 避免交易所 ticker 节奏差异；\n- 避免实现复杂度；\n- 当前目标是判断市场方向，而不是交易所间价差。\n\nP2 可增加多交易所确认：\n\n```text\nprimary 市场 impulse\n+ 至少一个 backup exchange 同方向\n```\n\n但 backup 数据不能作为额外币种混入 breadth 分母。\n\n---\n\n## 13. Pipeline 接入\n\n当前架构保持：\n\n```text\nExchange WS\n    ↓\nconsumeTickers\n    ↓\nper-symbol detectors\n    ↓\nevent aggregator\n    ↓\nalert policy\n    ↓\nTelegram\n```\n\n新增：\n\n```text\nExchange WS\n    ↓\nconsumeTickers\n    ├── PriceVelocityDetector\n    ├── VolumeSpikeDetector\n    └── MarketPulseDetector\n```\n\nPipeline 增加：\n\n```go\nmarketPulseDet *detector.MarketPulseDetector\n```\n\n初始化位置：\n\n```text\n完成 symbol discovery 之后\n启动 ticker goroutine 之前\n```\n\n消费位置：\n\n```go\nif p.marketPulseDet != nil && es.name == p.cfg.Exchanges.Primary {\n    p.marketPulseDet.OnTicker(es.name, t)\n}\n```\n\n事件通道：\n\n```go\nif p.marketPulseDet != nil {\n    eventChs = append(eventChs, p.marketPulseDet.Events())\n}\n```\n\n### 13.1 Universe 更新接口\n\n```go\nfunc (d *MarketPulseDetector) UpdateUniverse(symbols []string)\n```\n\n在：\n\n- 初次 symbol discovery；\n- refresh loop 成功刷新 primary universe；\n\n调用该方法。\n\n---\n\n## 14. # Goal Prompt

# Goal: 市场整体异动监控（Market Pulse）

> 状态：Draft / 可直接执行  
> 目标仓库：`ArchdevilForge/kairos`  
> 建议路径：`docs/GOAL_MARKET_PULSE.md`  
> 核心原则：只有市场从安静状态切换到整体活跃时才叫醒用户；单币异动只用于解释谁在领涨或领跌。  
> 实施优先级：P0 价格广度 → P1 告警门控 → P2 衍生品确认 → P3 板块扩散。

---

## 0. 一句话目标

将 Kairos 从“监控某个币突然涨跌”升级为：

> 监控整个加密永续市场何时从安静切换为同步上涨、同步下跌、趋势扩散或系统性高波动，只在真正值得打开盘面时发送 Telegram 告警。

最终 Kairos 应回答三个问题：

1. **现在是否值得看盘？**
2. **市场整体正在向上、向下，还是只有局部币种异动？**
3. **哪些币最能代表这次市场趋势？**

---

## 1. 背景与当前问题

Kairos 当前已经具备：

- 订阅成交量靠前的永续合约；
- WebSocket 实时 ticker；
- 单币价格速度检测；
- 单币成交量、OI、资金费率等检测器扩展位；
- 统一的事件 aggregator；
- Telegram 告警、去重和冷却；
- 单币多维度 resonance scorer。

但当前告警核心仍然是：

```text
某个 symbol 在 60 秒或 120 秒内达到价格变化阈值
```

这会产生以下问题：

1. 单币拉盘、插针、消息币异动会叫醒用户；
2. 大量独立告警不代表市场存在可交易趋势；
3. 用户打开盘面后，经常发现 BTC、ETH 和绝大多数币都没有同步；
4. 单币事件无法直接判断行情是否具有扩散性和持续性；
5. 告警关注的是“发生了什么”，而不是“现在值不值得看盘”。

因此需要新增一个横跨所有监控币种的市场级检测层。

---

## 2. 第一性原理

一个值得打开盘面的市场异动，通常至少具备以下特征：

### 2.1 广度

不是一个币在动，而是足够多的高流动性币种同时朝一个方向移动。

### 2.2 幅度

市场典型币种的涨跌幅超过正常短周期噪声，而不是仅仅多数币微涨 0.01%。

### 2.3 同步性

异动在相近时间内发生，而不是部分币一小时前涨、另一部分币刚开始涨。

### 2.4 持续性

条件持续多个采样周期，排除瞬时插针、WebSocket 抖动和盘口噪声。

### 2.5 核心资产确认

BTC、ETH 至少有一个与市场方向一致。若 BTC、ETH 完全不动，仅小币异动，更可能是局部板块行情。

### 2.6 非集中驱动

不能因为一个或两个高波动币暴涨，就把整个市场判定为上涨。

因此市场级检测不能只使用平均涨幅，必须同时使用：

```text
市场中位收益率
+ 上涨/下跌广度
+ 标准化异常程度
+ 持续确认
+ BTC/ETH 核心确认
+ 数据新鲜度
```

## 3. Goal

### 3.1 主目标

新增 `MarketPulseDetector`，实时聚合当前监控 universe 的 ticker，识别并输出以下市场状态事件：

```text
market_impulse
market_trend
market_stress
market_decay
```

并维护以下状态机：

```text
QUIET
IMPULSE_UP
IMPULSE_DOWN
TRENDING_UP
TRENDING_DOWN
STRESS_UP
STRESS_DOWN
DECAY
```

### 3.2 用户体验目标

默认情况下：

- `QUIET` 时不发送普通单币价格异动；
- 市场进入 `IMPULSE_*` 时发送一次叫醒告警；
- 市场进入 `TRENDING_*` 时发送一次趋势确认；
- 市场进入 `DECAY` 时可选发送趋势衰减；
- 每条市场告警附带领涨或领跌币；
- 避免同一轮行情重复刷屏。

### 3.3 工程目标

- 不新增独立微服务；
- 不引入 Kafka、Redis 等额外基础设施；
- 复用现有 ticker、aggregator、alert policy、Telegram 和 config；
- 保持 Go 单体结构；
- 核心算法必须确定性、可解释、可回放；
- 不让 LLM 进入生产判断路径。

## 5. 核心术语

### 5.1 Universe

本次市场统计实际参与计算的币种集合。

默认：

```text
primary exchange 上按 quote volume 排序的 Top 30 USDT 永续合约
```

### 5.2 Fresh Symbol

在 `freshnessSeconds` 内收到过有效 ticker 的币种。

### 5.3 Fresh Ratio

```text
fresh symbols / eligible symbols
```

新鲜度不足时禁止产生市场告警。

### 5.4 Breadth

满足方向条件的币种占有效币种比例。

```text
up_breadth = count(return > noise_threshold) / valid_count
down_breadth = count(return < -noise_threshold) / valid_count
```

### 5.5 Market Median Return

所有有效币种滚动收益率的中位数。

使用中位数而不是均值，避免极端币种污染。

### 5.6 Median Z

每个币滚动收益率除以自身近期 EWMA 波动率后，取横截面中位数。

### 5.7 Leader

相对于市场中位收益率表现最强或最弱的币种。

## 6. 事件定义

## 6.1 `market_impulse`

含义：

> 市场从安静状态突然进入同步移动，值得立即打开盘面。

事件方向：

```text
up
down
```

建议初始条件：

```text
fresh_ratio >= 0.80
valid_symbols >= 15
同方向 breadth >= 0.65
abs(median_return_60s) >= 0.18%
abs(median_z_60s) >= 1.5
BTC 或 ETH 至少一个同方向
最近 4 个采样中至少 3 个满足
```

输出字段：

```json
{
  "direction": "up",
  "state_from": "QUIET",
  "state_to": "IMPULSE_UP",
  "window_seconds": 60,
  "median_return_pct": 0.23,
  "median_z": 1.82,
  "breadth": 0.76,
  "advancers": 22,
  "decliners": 4,
  "neutral": 3,
  "valid_symbols": 29,
  "fresh_ratio": 0.97,
  "btc_return_pct": 0.31,
  "eth_return_pct": 0.37,
  "leaders": ["SOL", "DOGE", "AVAX"],
  "laggards": ["TRX", "XMR", "BCH"]
}
```

## 6.2 `market_trend`

含义：

> 市场启动后，方向继续扩散并持续，短周期趋势得到确认。

建议条件：

```text
当前状态为 IMPULSE_UP 或 IMPULSE_DOWN
同方向 breadth >= 0.60
abs(median_return_300s) >= 0.45%
方向持续 >= 180 秒
最近 6 个采样中至少 5 个方向一致
期间未进入反向 impulse
```

趋势状态：

```text
TRENDING_UP
TRENDING_DOWN
```

## 6.3 `market_stress`

含义：

> 市场出现极端同步移动、恐慌下跌或逼空上涨。

建议条件：

```text
fresh_ratio >= 0.80
同方向 breadth >= 0.80
abs(median_return_60s) >= 0.35%
abs(median_z_60s) >= 2.5
```

后续 P2 可叠加：

```text
全市场爆仓异常
OI 广度异常
成交量广度异常
```

## 6.4 `market_decay`

含义：

> 已确认趋势开始失去广度或方向一致性，继续盯盘价值下降。

建议条件：

```text
当前为 TRENDING_UP / TRENDING_DOWN
同方向 breadth 连续 60 秒低于 0.50
或 median_return_60s 接近 0
或反方向 breadth 高于 0.45
```

默认可配置是否发送 Telegram。

状态变化事件不受普通 cooldown 限制
stress 事件 cooldown = 5 分钟

P0 可从 `QUIET` 冷启动。

P1 可将当前状态与最近快照保存到 SQLite，重启后恢复，避免服务重启重复发送 impulse。

## 10. 收益率与标准化

### 10.1 收益率

```text
return_pct = (price_now / price_then - 1) * 100
```

### 10.2 噪声区间

默认：

```text
noiseReturnPct = 0.08
```

分类：

```text
return > +0.08%  => advancer
return < -0.08%  => decliner
其他             => neutral
```

### 10.3 EWMA 波动率

建议使用 1 分钟收益的 EWMA 方差：

```text
variance_t = alpha * r_t² + (1 - alpha) * variance_previous
z = return_60s / max(sqrt(variance), volatility_floor)
```

初始：

```text
alpha = 0.10
volatility_floor_pct = 0.03
```

若 P0 时间有限，可先不使用 Z 作为硬门槛，只记录日志；但必须预留字段和测试。

## 11. Universe 管理

当前 universe 会定时刷新，MarketPulse 必须正确处理成员变化。

### 11.1 参与条件

一个币参与计算必须满足：

```text
存在于当前 primary exchange universe
不是 blacklist
last price > 0
最近 freshnessSeconds 内收到 ticker
已有至少 warmupSeconds 历史
目标窗口存在可用历史价格
```

### 11.2 新币 warmup

默认：

```text
warmupSeconds = 300
```

新加入 universe 的币在 warmup 完成前不参与市场统计。

### 11.3 被移除的币

从 eligible universe 移除，但其历史缓存可延迟 15 分钟清理。

### 11.4 Universe 变化保护

universe 刷新后的 60 秒内：

- 可以继续计算；
- 禁止仅因成员变化触发新状态；
- 若有效样本少于 `minValidSymbols`，保持原状态或进入数据不足状态，不发送方向告警。

## 12. 多交易所策略

P0 只使用：

```text
cfg.Exchanges.Primary
```

原因：

- 避免同一币在多个交易所重复计数；
- 避免交易所 ticker 节奏差异；
- 避免实现复杂度；
- 当前目标是判断市场方向，而不是交易所间价差。

P2 可增加多交易所确认：

```text
primary 市场 impulse
+ 至少一个 backup exchange 同方向
```

但 backup 数据不能作为额外币种混入 breadth 分母。

## 24. 性能与并发要求

### 24.1 性能目标

Top 30 universe 下：

```text
每次 snapshot 计算 < 10ms
常驻内存增量 < 50MB
不因 market detector 阻塞 ticker 消费
```

### 24.2 并发原则

- `OnTicker` 尽量快速；
- 可只更新缓存，由内部 ticker 每 5 秒计算 snapshot；
- 计算过程中避免长期持有写锁；
- event channel 使用有限缓冲；
- channel 满时记录告警，不阻塞行情入口；
- 所有 goroutine 响应 context cancel。

推荐结构：

```text
OnTicker:
  update symbol cache
  return

snapshotLoop every 5s:
  copy required state
  unlock
  calculate
  evaluate state
  emit
```

## 25. 失败与降级策略

### 数据不足

```text
不改变方向状态
不发送新市场告警
记录 gated reason
```

若数据不足持续超过 60 秒：

```text
内部状态标记 DATA_DEGRADED
可选发送一次系统告警
```

### BTC/ETH 缺失

如果要求核心确认：

```text
禁止触发普通 impulse
stress 可配置允许 breadth 单独触发
```

### Detector panic

不得影响整个 Pipeline。关键 goroutine 应由 errgroup 管理，必要位置增加 recover 并记录。

### Telegram 失败

不回滚市场状态，但记录发送失败。可选存储 pending notification，第一版不要求重试队列。
